# Спецификация MVP: Mobile Gallery → Figma

Версия 2 для проверки, 2026-10-11. Продуктовый код по ней ещё не написан.

Связанный документ: [feasibility.md](feasibility.md) — результаты технического эксперимента, на которых основаны решения ниже.

## 1. Цель и границы

**Цель.** Пользователь выбирает изображения в галерее телефона, нажимает «Отправить в Figma», и они появляются сеткой на текущей странице открытого файла Figma.

**Для кого.** Личный инструмент одного пользователя: один компьютер, один открытый плагин, телефоны в той же Wi-Fi-сети. Телефоны запускают приложение через Expo Go.

**Критерий успеха.** Пять изображений, выбранных на телефоне, через несколько секунд лежат на странице Figma узлами шириной 400 px, а телефон показывает «Вставлено» по каждому.

**Не входит в MVP:**

- выбор файла или страницы Figma с телефона, Figma REST API;
- облачный сервер, аккаунты, несколько пользователей, сопряжение по коду или QR;
- автоматическое обнаружение скриншотов, фоновая отправка, съёмка камерой;
- видео, HEIC на стороне сервера, анимированные GIF;
- постоянное хранилище очереди;
- сохранение списка изображений на телефоне между запусками приложения;
- автоматический поиск сервера в сети;
- несколько одновременно открытых плагинов.

## 2. Архитектура

```
Телефон (Expo Go) ──HTTP──▶ Сервер (Fastify) ◀──HTTP── iframe плагина ──postMessage──▶ main-поток плагина
   http://<LAN-IP>:8787      очередь в памяти          http://localhost:8787            figma.currentPage
                             + временные файлы
```

| Компонент | Папка | Ответственность |
|---|---|---|
| Мобильное приложение | `mobile/` | Выбор изображений, отправка, показ статусов, настройки подключения |
| Сервер | `server/` | Приём и проверка файлов, очередь заданий, выдача заданий плагину, хранение статусов |
| Плагин Figma | `figma-plugin/` | Получение заданий, уменьшение больших изображений, вставка и раскладка, подтверждение |
| Документация | `docs/` | Спецификация, результаты проверок, инструкции подключения |

Три пакета независимы: у каждого свой `package.json`, общих зависимостей и общего кода нет. Контракт между ними — HTTP API из раздела 6.

**Разделение внутри плагина** (подтверждено экспериментом):

- iframe выполняет сетевые запросы и уменьшает изображения через canvas;
- main-поток вставляет изображения, ведёт раскладку и учёт вставленных заданий.

**Правила, которые сохраняют путь к будущему переносу сервера:**

1. Клиенты знают только «базовый адрес + токен». Адрес в коде не зашит.
2. Авторизация только через заголовок.
3. Плагин получает файлы по HTTP, а не с диска.

## 3. Пользовательские сценарии

### 3.1. Первый запуск

1. Пользователь указывает в `server/.env` сетевой интерфейс Wi-Fi и запускает сервер.
2. Сервер печатает адрес для телефона и путь к файлу с токеном.
3. Пользователь импортирует плагин в настольное приложение Figma, запускает его и вставляет токен.
4. Пользователь открывает приложение на телефоне, в настройках вводит адрес и токен, нажимает «Проверить соединение».

### 3.2. Отправка изображений

1. В Figma открыт нужный файл, плагин запущен и показывает «Подключено».
2. На телефоне пользователь нажимает «Выбрать изображения» и отмечает одно или несколько.
3. Проверяет превью, при необходимости удаляет лишние.
4. Нажимает «Отправить в Figma».
5. Каждое изображение проходит статусы «Отправка» → «В очереди» → «Вставляется» → «Вставлено».
6. Изображения появляются на текущей странице Figma.

### 3.3. Плагин закрыт во время отправки

Изображения загружаются на сервер и остаются в статусе «В очереди». Телефон показывает подсказку «Плагин в Figma не запущен». Когда пользователь запускает плагин, он забирает очередь. Задания, не забранные за 30 минут, истекают.

### 3.4. Сбой сети или сервера

Телефон показывает ошибку у конкретного изображения и кнопку «Повторить». Повтор безопасен: изображение не вставится дважды (раздел 5.6).

### 3.5. Сменился IP-адрес компьютера

Сервер при следующем запуске печатает новый адрес. Телефон показывает ошибку соединения с подсказкой, пользователь меняет адрес в настройках (раздел 9).

## 4. Форматы и ограничения

### 4.1. Что принимает сервер

| Параметр | Ограничение |
|---|---|
| Форматы | PNG, JPEG, GIF. Определяются по содержимому файла, а не по заявленному типу |
| Размер исходного файла | не больше 20 МБ (20 × 1024 × 1024 байт) |
| Сторона изображения | от 1 до 16 384 px |
| Площадь изображения | не больше 50 мегапикселей |

Размеры в пикселях сервер читает из заголовка файла, не декодируя изображение. Лимит 50 Мп выбран так, чтобы проходили снимки 48 Мп (8064×6048) и чтобы декодирование в iframe плагина не требовало больше примерно 200 МБ памяти. Снимки 200 Мп отклоняются.

HEIC, WebP, AVIF и остальные форматы сервер отклоняет.

### 4.2. Что делает телефон

На iOS системный picker вызывается в режиме `Compatible`. Фото в HEIC он отдаёт как JPEG (проверено на iOS 26.4; файл получается примерно вдвое больше исходного). Если picker всё же вернул неподдерживаемый формат, сервер его отклонит, и телефон покажет ошибку формата.

### 4.3. Что делает плагин

- Figma принимает изображения не больше 4096 px по каждой стороне.
- Если любая сторона больше 4096 px, iframe плагина уменьшает изображение до 4096 px по большей стороне с сохранением пропорций и передаёт результат в PNG.
- Если обе стороны не больше 4096 px, в Figma передаются исходные байты без изменений.

Фото с камеры iPhone (4284×5712) больше лимита, поэтому уменьшение срабатывает на обычных снимках.

### 4.4. GIF

**Поддерживается только статичное изображение.** Анимация в MVP не поддерживается и не проверяется.

- GIF не больше 4096 px передаётся в Figma без изменений. Как Figma покажет анимированный файл, спецификация не определяет.
- GIF больше 4096 px уменьшается так же, как остальные форматы, и превращается в статичный PNG из первого кадра.

### 4.5. Вставка и раскладка

**Узел.** Прямоугольник с заливкой-изображением. Ширина 400 px, высота `round(400 × высота / ширина)` исходника, но не меньше 1 px. Узел добавляется на верхний уровень страницы, которая является текущей в момент вставки.

**Сетка.** 5 колонок, шаг колонки 440 px (ширина 400 + отступ 40). Узлы в строке выровнены по верхнему краю. Отступ между строками 40 px от нижнего края самого высокого узла строки.

**Состояние раскладки** хранится в данных плагина на странице, у каждой страницы своё:

| Поле | Значение |
|---|---|
| `originX` | Левый край текущего блока |
| `rowY` | Верхний край текущей строки |
| `rowHeight` | Высота самого высокого узла в текущей строке |
| `col` | Номер следующей свободной колонки, от 0 до 5 |

**Занятые области** — это рамки (`absoluteBoundingBox`) всех узлов верхнего уровня страницы: существующий контент пользователя и ранее вставленные изображения. Скрытые и заблокированные узлы тоже считаются.

**Алгоритм для каждого нового изображения** с высотой узла `h`:

1. Если состояния нет, начать новый блок (шаг 5).
2. Если `col` равен 5, перейти на новую строку: `rowY = rowY + rowHeight + 40`, `rowHeight = 0`, `col = 0`.
3. Кандидат — прямоугольник `x = originX + col × 440`, `y = rowY`, размер 400 × `h`.
4. Если кандидат не пересекается ни с одной занятой областью, занять его (шаг 6).
5. Иначе начать новый блок:
   - на пустой странице: `originX = 0`, `rowY = 0`;
   - на непустой: `originX` — минимальный левый край занятых областей, `rowY` — максимальный нижний край плюс 100 px;
   - `rowHeight = 0`, `col = 0`, кандидат пересчитывается по шагу 3. Ниже всего контента пересечений быть не может.
6. Создать узел в позиции кандидата, затем `rowHeight = max(rowHeight, h)`, `col = col + 1`, сохранить состояние.

Пересечением считается наложение площадей. Касание краями пересечением не считается.

**Что это гарантирует:**

- Новое изображение в момент вставки не перекрывает ни один узел верхнего уровня: ни контент пользователя, ни изображения прошлых отправок.
- Повторные отправки продолжают ту же сетку с первой свободной ячейки, в том числе после перезапуска плагина.
- Если пользователь занял будущую ячейку своим объектом или сдвинул контент, сетка не накладывается на него, а начинается новым блоком ниже всего содержимого страницы.
- Существующие узлы плагин не перемещает и не изменяет.

**Ограничения:**

- Учитывается рамка узла без теней и обводок: тень чужого объекта может визуально зайти на изображение.
- Гарантия действует на момент вставки. Если пользователь позже сам передвинет объект на изображение, плагин ничего не исправляет.
- Новый блок может оказаться далеко от места, где пользователь сейчас работает.

**Область просмотра.** Когда очередь заданий опустела, плагин один раз прокручивает область просмотра к изображениям, вставленным с момента предыдущей прокрутки. Выделение пользователя плагин не меняет.

## 5. Жизненный цикл задания

Одно изображение — одно задание.

### 5.1. Идентификатор

Идентификатор задания создаёт телефон в момент выбора изображения (UUID v4). Он не меняется при повторных отправках того же выбранного изображения. На этом построена защита от дубликатов: и сервер, и плагин узнают повтор по идентификатору.

Чтобы намеренно вставить то же фото второй раз, пользователь выбирает его в галерее заново. Тогда оно получает новый идентификатор.

### 5.2. Состояния на сервере

| Состояние | Значение | Конечное |
|---|---|---|
| `queued` | Файл принят, ждёт плагин | нет |
| `leased` | Плагин забрал задание и ещё не ответил | нет |
| `inserted` | Плагин подтвердил вставку | да |
| `failed` | Вставка не удалась, причина записана | да |
| `expired` | Плагин не забрал задание за 30 минут | да |

Причины состояния `failed`:

| Код | Значение |
|---|---|
| `decode_failed` | Плагин не смог прочитать изображение |
| `insert_failed` | Figma вернула ошибку при вставке |
| `plugin_no_ack` | Плагин трижды забрал задание и ни разу не ответил |

### 5.3. Аренда

Аренда — это время, на которое задание закреплено за плагином.

- Аренда начинается в момент, когда сервер отдаёт задание в ответе на `GET /api/jobs/next`, и длится 60 секунд.
- За это время плагин должен скачать файл, вставить изображение и отправить подтверждение.
- Плагин аренду не продлевает. Скачивание файла её не продлевает.
- Пока задание в `leased`, оно не выдаётся повторно.
- Каждая выдача увеличивает счётчик попыток `attempts` на 1. Задание выдаётся не больше 3 раз.
- Если аренда истекла без ответа и `attempts` меньше 3, задание возвращается в `queued`. Очередь упорядочена по времени создания, поэтому оно будет выдано раньше более новых заданий.
- Если аренда истекла без ответа и `attempts` равен 3, задание становится `failed` с причиной `plugin_no_ack`.
- Сервер проверяет сроки раз в 5 секунд и дополнительно при каждом запросе задания или его статуса. Состояние меняется не позже чем через 5 секунд после срока.

### 5.4. Переходы

| Событие | Из | В | Действие сервера |
|---|---|---|---|
| Загрузка с новым идентификатором | — | `queued` | Сохраняет файл, `attempts = 0`, начинает отсчёт 30 минут |
| Плагин запросил следующее задание | `queued` | `leased` | Выдаёт самое старое задание, `attempts + 1`, срок аренды 60 с |
| Подтверждение «вставлено» | любое | `inserted` | Удаляет файл, если он ещё есть |
| Сообщение об ошибке от плагина | `queued`, `leased` | `failed` | Удаляет файл, сохраняет причину |
| Аренда истекла, `attempts` < 3 | `leased` | `queued` | — |
| Аренда истекла, `attempts` = 3 | `leased` | `failed` | Причина `plugin_no_ack`, удаляет файл |
| 30 минут с момента постановки в очередь | `queued` | `expired` | Удаляет файл |
| Час после перехода в конечное состояние | конечное | запись удалена | — |
| Повторная загрузка, тот же идентификатор | `queued`, `leased`, `inserted` | без изменений | Возвращает текущее состояние, тело запроса игнорирует |
| Повторная загрузка, тот же идентификатор | `failed`, `expired` | `queued` | Сохраняет новый файл, `attempts = 0`, отсчёт 30 минут заново |

**Подтверждение «вставлено» принимается из любого состояния**, включая `failed` и `expired`. Изображение уже лежит в Figma, и статус должен это отражать. Пример: плагин вставил изображение, но ответил после третьего истечения аренды.

Сообщение об ошибке для задания, которое уже `inserted`, сервер отклоняет: вставленное остаётся вставленным.

### 5.5. Гарантия завершения

Каждое принятое задание приходит в конечное состояние, пока сервер работает:

- в `queued` задание находится не дольше 30 минут: дальше `expired`;
- в `leased` — не дольше 60 секунд за одну выдачу и не больше трёх выдач: дальше `failed` с `plugin_no_ack`;
- отсчёт 30 минут во время аренды не останавливается.

Наибольшее время до конечного состояния — около 31 минуты. Зависнуть в незавершённом состоянии задание не может.

У каждого конечного состояния есть понятный статус на телефоне (раздел 5.7). Запись о задании хранится час после завершения. Телефон к этому времени уже получил конечный статус и больше его не запрашивает.

Единственный случай потери — перезапуск сервера (раздел 5.8). Он тоже показывается явным статусом.

### 5.6. Защита от дубликатов

Плагин отмечает каждую вставку тремя метками:

| Метка | Где хранится | Когда записывается | Что защищает |
|---|---|---|---|
| Идентификатор в данных узла | в самом изображении | в том же шаге, что и создание узла | Позволяет найти, каким заданием создан узел |
| Список вставленных в данных документа | в файле Figma, последние 500 | в том же шаге, что и создание узла | Повтор в том же файле, на любой странице |
| Список вставленных в `figma.clientStorage` | на компьютере, последние 500 | сразу после вставки | Повтор, когда плагин открыт уже в другом файле |

Создание узла, запись идентификатора в узел, запись в список документа и обновление раскладки выполняются **одним синхронным шагом без ожиданий**. Ширину и высоту изображения main-поток получает от iframe вместе с байтами и ничего не запрашивает асинхронно. Поэтому плагин не может быть закрыт так, чтобы узел уже существовал, а отметки в документе ещё не было.

**Порядок обработки задания:**

1. iframe получил задание от сервера и передал идентификатор в main-поток.
2. main-поток проверяет оба списка. Если идентификатор найден — **пропуск**: файл не скачивается, узел не создаётся, переход к шагу 7.
3. iframe скачивает файл, декодирует и при необходимости уменьшает. При ошибке отправляет серверу `failed` с `decode_failed`, обработка задания окончена.
4. iframe передаёт в main-поток байты, ширину и высоту.
5. main-поток ещё раз проверяет список документа. Затем одним синхронным шагом: вычисляет позицию, создаёт узел, записывает идентификатор в узел, добавляет его в список документа, сохраняет раскладку. Если Figma вернула ошибку, узел не создаётся, серверу отправляется `failed` с `insert_failed`.
6. main-поток добавляет идентификатор в список в `figma.clientStorage`.
7. iframe отправляет серверу подтверждение «вставлено». При сетевой ошибке повторяет его раз в 2 секунды, пока плагин открыт. Следующее задание плагин берёт, не дожидаясь успеха этого повтора.

**Аварийное завершение плагина** (закрыт пользователем, сбой Figma, выключение компьютера):

| Момент завершения | Состояние | Что дальше | Дубликат |
|---|---|---|---|
| До шага 5 | Узла нет, отметок нет | Аренда истекает, задание выдаётся снова и вставляется | нет |
| После шага 5, до шага 6 | Узел и отметка в документе есть, в `clientStorage` отметки нет, сервер не знает о вставке | Аренда истекает, задание выдаётся снова. Плагин в том же файле находит идентификатор в списке документа и только подтверждает | нет |
| То же, но плагин затем запущен в другом файле | В том файле отметки нет | Изображение вставляется во второй файл | **возможен**, в другом файле |
| После шага 6, до успешного шага 7 | Обе отметки есть, сервер не знает о вставке | Аренда истекает, задание выдаётся снова. Плагин находит идентификатор и только подтверждает, в любом файле | нет |
| Figma закрылась, не сохранив изменения шага 5 | Узел и отметка в документе пропали вместе | Задание выдаётся снова. Если отметка в `clientStorage` успела записаться, изображение не вставится и останется только статус «Вставлено» | нет; возможна **потеря** изображения |

Если после сбоя плагин не запускают 30 минут, задание становится `expired`. Если плагин каждый раз берёт задание и завершается, не ответив, после третьей выдачи оно становится `failed` с `plugin_no_ack`. В обоих случаях пользователь нажимает «Повторить», и срабатывает та же проверка: дубликата не будет.

**Другие случаи повтора:**

| Случай | Что происходит | Дубликат |
|---|---|---|
| Телефон не получил ответ на загрузку и отправил её снова | Сервер находит задание по идентификатору и возвращает его состояние | нет |
| Сервер перезапущен после вставки, телефон нажал «Повторить» | Создаётся задание с тем же идентификатором. Плагин находит его в списках и только подтверждает | нет |
| Пользователь отменил вставку через Undo | Узел исчез, отметка в `clientStorage` осталась. Повтор того же задания изображение не вернёт | нет |
| Пользователь удалил изображение вручную | То же | нет |
| Плагин запущен под другим профилем Figma или на другом компьютере, в другом файле | Обоих списков там нет | возможен; вне сценария MVP |

Чтобы вернуть удалённое изображение, пользователь выбирает фото в галерее заново.

### 5.7. Статусы на телефоне

| Статус | Откуда | Текст для пользователя | Действия |
|---|---|---|---|
| Выбрано | локально | — | Удалить |
| Отправка | локально | «Отправка…» | — |
| Ошибка отправки | локально: сеть или отказ сервера | Причина из раздела 8 | Повторить, удалить |
| В очереди | `queued` | «В очереди» | — |
| Вставляется | `leased` | «Вставляется…» | — |
| Вставлено | `inserted` | «Вставлено» | Убрать |
| Ошибка вставки | `failed`, `decode_failed` | «Файл повреждён или не читается» | Удалить |
| Ошибка вставки | `failed`, `insert_failed` | «Figma не приняла изображение» и текст ошибки | Повторить, удалить |
| Нет ответа от плагина | `failed`, `plugin_no_ack` | «Плагин не подтвердил вставку. Проверьте страницу в Figma. Повтор не создаст дубликат» | Повторить, удалить |
| Истекло | `expired` | «Плагин не забрал изображение за 30 минут» | Повторить, удалить |
| Статус неизвестен | сервер ответил 404 | «Сервер был перезапущен. Повтор не создаст дубликат» | Повторить, удалить |

«Повторить» всегда отправляет то же изображение с тем же идентификатором.

Телефон опрашивает статус каждого незавершённого задания раз в 2 секунды и прекращает опрос в конечном состоянии. Изображения загружаются по одному, по порядку.

Список изображений и их статусы живут, пока приложение открыто. После закрытия приложения список пуст. Уже загруженные задания при этом остаются на сервере и будут вставлены.

### 5.8. Перезапуск сервера

Очередь хранится в памяти. При перезапуске:

- все задания и статусы теряются;
- временная папка очищается при старте;
- телефон по незавершённым заданиям получает 404 и показывает «Статус неизвестен»;
- повтор с телефона безопасен благодаря разделу 5.6.

SQLite в MVP не используется: защита от дубликатов держится на плагине, а потерянную очередь пользователь восстанавливает кнопкой «Повторить».

## 6. HTTP API

Базовый путь `/api`. Ответы в JSON, кроме выдачи файла.

**Авторизация.** Все запросы, кроме `GET /api/health` и `OPTIONS`, требуют заголовок `Authorization: Bearer <токен>`. Токен в URL не принимается. Без верного токена ответ `401`.

**CORS.** Сервер отвечает на `OPTIONS` и добавляет ко всем ответам `Access-Control-Allow-Origin: *` и разрешение заголовков `Authorization`, `Content-Type`. Это требование среды плагина: у его iframe origin равен `null`.

**Формат ошибки:** `{ "error": { "code": "<код>", "message": "<текст>" } }`.

**Объект задания:**

```json
{
  "id": "5f0c2a4e-8b1d-4c57-9a3e-2d7f6b1c9e10",
  "status": "queued",
  "mimeType": "image/jpeg",
  "bytes": 4130716,
  "width": 4284,
  "height": 5712,
  "attempts": 0,
  "error": null,
  "createdAt": "2026-10-11T10:24:59.921Z",
  "updatedAt": "2026-10-11T10:24:59.921Z"
}
```

### 6.1. `GET /api/health`

Без авторизации. Если заголовок с токеном передан, сервер сообщает, верен ли он.

```json
{ "service": "mobile-gallery", "ok": true, "authorized": true, "pluginConnected": true }
```

- `service` — постоянная строка. По ней клиент убеждается, что по адресу отвечает именно этот сервер, а не другое устройство.
- `authorized` — `true` при верном токене, `false` при неверном или отсутствующем.
- `pluginConnected` — признак активности плагина, правило в разделе 9.3.

### 6.2. `POST /api/uploads`

Загрузка одного изображения. Тело запроса — байты файла.

| Заголовок | Значение |
|---|---|
| `Authorization` | `Bearer <токен>` |
| `Content-Type` | `image/png`, `image/jpeg` или `image/gif` |
| `X-Job-Id` | UUID v4, созданный телефоном |

Ответы:

| Код | Когда | Тело |
|---|---|---|
| `201` | Создано новое задание либо перезапущено задание из `failed` или `expired` | объект задания |
| `200` | Задание с таким идентификатором уже есть в `queued`, `leased` или `inserted` | объект задания |
| `400` `invalid_job_id` | Заголовок `X-Job-Id` отсутствует или не UUID | ошибка |
| `401` `unauthorized` | Нет токена или он неверен | ошибка |
| `413` `file_too_large` | Файл больше 20 МБ | ошибка |
| `415` `unsupported_type` | Содержимое не PNG, JPEG или GIF, либо не совпадает с `Content-Type` | ошибка |
| `422` `invalid_dimensions` | Размеры не читаются или выходят за пределы раздела 4.1 | ошибка |

### 6.3. `GET /api/jobs/next`

Для плагина. Выдаёт самое старое задание из `queued` и переводит его в `leased`.

```json
{ "job": { "id": "…", "status": "leased", "…": "…" }, "pending": 3 }
```

Если заданий нет: `{ "job": null, "pending": 0 }`. Поле `pending` — число заданий в `queued` после выдачи.

### 6.4. `GET /api/jobs/:id/file`

Для плагина. Возвращает байты файла с `Content-Type` задания.

| Код | Когда |
|---|---|
| `200` | Файл есть |
| `404` `job_not_found` | Задания нет |
| `410` `file_gone` | Задание в конечном состоянии, файл удалён |

Этой точки не было в исходном списке. Она добавлена, чтобы `GET /api/jobs/next` возвращал обычный JSON, а не файл со служебными заголовками.

### 6.5. `GET /api/jobs/:id`

Для телефона. Возвращает объект задания или `404` `job_not_found`.

### 6.6. `POST /api/jobs/:id/ack`

Для плагина. Тело запроса:

```json
{ "result": "inserted" }
```

или

```json
{ "result": "failed", "reason": "decode_failed", "message": "The source image could not be decoded." }
```

Допустимые `reason` от плагина: `decode_failed`, `insert_failed`. Причину `plugin_no_ack` ставит только сервер.

| Запрос | Состояние задания | Код | Результат |
|---|---|---|---|
| `inserted` | любое | `200` | Задание становится или остаётся `inserted` |
| `failed` | `queued`, `leased` | `200` | Задание становится `failed` |
| `failed` | `failed`, `expired` | `200` | Без изменений |
| `failed` | `inserted` | `409` `job_finished` | Без изменений |
| любой | задания нет | `404` `job_not_found` | — |
| тело не по формату | — | `400` `invalid_ack` | — |

При коде `200` возвращается объект задания.

| Ситуация | Сервер | Плагин | Телефон |
|---|---|---|---|
| Сервер не запущен или недоступен | — | «Сервер недоступен», повторяет попытки | «Ошибка отправки» или плашка «Сервер недоступен», кнопка «Повторить» |

| Файл больше 20 МБ | `413` | — | «Файл больше 20 МБ» |
| Неподдерживаемый формат или подмена типа | `415` | — | «Формат не поддерживается. Подходят PNG, JPEG, GIF» |
| Недопустимые размеры | `422` | — | «Изображение слишком большое» |
| Повреждённый файл с верным заголовком | Принимает: полное декодирование сервер не делает | Не может декодировать, отправляет `failed` с `decode_failed` | «Ошибка вставки: файл повреждён» |

| Сервер перезапущен | Очередь потеряна | Продолжает опрос | «Статус неизвестен», кнопка «Повторить» |
| Телефон потерял сеть во время отправки | — | — | «Ошибка отправки», кнопка «Повторить» |

Телефон и плагин не показывают пользователю технический текст без пояснения: к каждому коду ошибки привязано понятное сообщение.

## 9. Подключение по локальной сети

### 9.1. Адрес привязки сервера

Сервер **не слушает все интерфейсы**. Он открывает порт ровно на двух адресах:

1. `127.0.0.1` — для плагина;
2. IPv4-адрес одного сетевого интерфейса — для телефона.

Интерфейс задаётся именем в `server/.env`: `LAN_INTERFACE=en0`. Имя вместо адреса выбрано потому, что IP может меняться, а имя интерфейса постоянно.

- Если `LAN_INTERFACE` не задан, сервер слушает только `127.0.0.1`, печатает список интерфейсов с адресами и объясняет, что телефон подключиться не сможет.
- Если у указанного интерфейса нет IPv4-адреса, сервер не запускается и печатает список доступных интерфейсов.
- При запуске сервер печатает адрес для телефона, например `http://192.168.1.10:8787`.

Проверено на компьютере разработки 2026-10-11:

| Интерфейс | Адрес | Что это |
|---|---|---|
| `lo0` | `127.0.0.1` | Локальная петля |
| `en0` | `192.168.1.10` | Wi-Fi, через него идёт маршрут по умолчанию |
| `utun4` | `10.0.0.1` | VPN-туннель (точка-точка) |

Для этого компьютера значение `LAN_INTERFACE=en0`. Интерфейс VPN серверу не нужен.

### 9.2. Смена LAN-IP

- IP компьютера может измениться после переподключения к Wi-Fi или перезагрузки роутера.
- Сервер определяет адрес интерфейса при запуске. Если адрес изменился во время работы, сервер нужно перезапустить.
- Телефон адрес не определяет сам: пользователь вводит новый адрес в настройках.
- Если старый адрес достался другому устройству, оно может ответить на запрос телефона. Телефон отличает это по полю `service` (раздел 9.3) и показывает «По этому адресу отвечает другое устройство. Проверьте адрес сервера».
- Рекомендация в документации: закрепить IP компьютера в настройках роутера (резервирование DHCP), тогда адрес не меняется.

### 9.3. Как определяется состояние подключения

**Как сервер узнаёт, что плагин активен.** Отдельного сигнала нет. Плагин, пока открыт, сам запрашивает задания раз в 2 секунды. Сервер запоминает время последнего авторизованного запроса к точкам, которыми пользуется только плагин: `GET /api/jobs/next`, `GET /api/jobs/:id/file`, `POST /api/jobs/:id/ack`.

`pluginConnected` равен `true`, если выполняется хотя бы одно условие:

- последний такой запрос был не больше 10 секунд назад;
- есть задание в `leased` с неистёкшей арендой. Это нужно, потому что во время обработки большого изображения плагин новых заданий не запрашивает.

Следствия:

- после закрытия плагина признак становится `false` через 10 секунд, а если плагин закрыт во время обработки задания — не позже чем через 60 секунд;
- признак говорит «плагин открыт в каком-то файле», а не «открыт в нужном файле»;
- телефон и плагин используют один токен, сервер различает их только по тому, к каким точкам они обращаются.

**Как плагин узнаёт о сервере.** По результату собственного запроса заданий: сетевая ошибка — «Сервер недоступен», код `401` — «Токен не подошёл», код `200` — «Подключено».

**Как телефон различает причины.** Телефон вызывает `GET /api/health` с токеном в заголовке, время ожидания 5 секунд:

| Что получил телефон | Вывод | Что видит пользователь |
|---|---|---|
| Сетевая ошибка или нет ответа за 5 с | Сервер недоступен | «Сервер недоступен» и подсказка «Как подключиться» |
| Ответ не JSON или `service` не `mobile-gallery` | По адресу отвечает не наш сервер | «По этому адресу отвечает другое устройство. Проверьте адрес сервера» |
| `authorized: false` | Токен неверный | «Токен неверный» и переход в настройки |
| `authorized: true`, `pluginConnected: false` | Сервер готов, плагина нет | «Плагин в Figma не запущен. Изображения подождут в очереди до 30 минут» |
| `authorized: true`, `pluginConnected: true` | Всё готово | Плашек нет |

Отсутствие плагина — не ошибка: отправка разрешена, изображения ждут в очереди.

Телефон вызывает `GET /api/health`:

- при открытии приложения и при возврате в него;
- по кнопке «Проверить соединение»;
- перед началом отправки;
- раз в 5 секунд, пока есть незавершённые задания.

Независимо от этого любой запрос телефона, получивший `401`, переводит приложение в состояние «Токен неверный», а любая сетевая ошибка — в «Сервер недоступен».

### 9.4. Подсказка «Как подключиться» в приложении

Показывается при ошибке соединения и в настройках:

1. Сервер запущен на компьютере, в его окне напечатан адрес для телефона.
2. Адрес в настройках совпадает с напечатанным, начинается с `http://` и заканчивается на `:8787`.
3. Телефон подключён к той же сети Wi-Fi, что и компьютер. Гостевая сеть не подходит.
4. VPN на телефоне выключен.
5. На iPhone приложению разрешён доступ к локальной сети: «Настройки → Конфиденциальность и безопасность → Локальная сеть».
6. Если на компьютере включён firewall, входящие подключения для сервера разрешены.

### 9.5. Что войдёт в `docs/connection.md`

Пошаговая настройка: как найти имя интерфейса Wi-Fi, как задать `LAN_INTERFACE`, где взять токен, как закрепить IP на роутере, как разрешить входящие подключения в firewall macOS, список типичных проблем. Проброс портов на роутере не настраивается и в документации не предлагается.

## 10. Безопасность

- **Токен.** Сервер создаёт случайный токен (128 бит) при первом запуске и сохраняет в `server/.token`. Файл не попадает в git. Токен сравнивается за постоянное время.
- **Токен — временный механизм для личного MVP.** Он один на телефон и плагин, не отзывается по отдельности и передаётся по HTTP без шифрования. Любое устройство в той же сети, перехватившее трафик, получит токен и изображения. Для публичного сервиса такой защиты недостаточно.
- **Токен не передаётся в URL** и не пишется в журнал сервера.
- **Сеть.** Сервер доступен только с этого компьютера и из одной выбранной сети. В интернет он не публикуется, проброс портов не используется.
- **Проверка файлов.** Тип определяется по содержимому, размер файла и размеры изображения ограничены (раздел 4.1). Имя файла с телефона не принимается: файлы на диске называются идентификатором задания.
- **Идентификатор задания** принимается только в формате UUID, поэтому не может содержать путь.
- **Временные файлы.** Лежат в отдельной папке внутри системной временной директории. Удаляются после вставки, ошибки или истечения срока, а также все разом при старте сервера.
- **Плагин.** Сетевой доступ ограничен манифестом: только `http://localhost:8787` в режиме разработки.
- **Защиты системы** (ATS на iOS, запрет cleartext на Android, firewall) глобально не отключаются.

## 11. Что проверено и что предстоит проверить

Подробности и источники — в [feasibility.md](feasibility.md).

### 11.1. Проверено на реальных устройствах

Одноразовым кодом эксперимента, iPhone с iOS 26.4 и Android 13 в Expo Go, настольное приложение Figma на macOS:

- телефон достаёт сервер по LAN-IP по HTTP, с токеном в заголовке;
- плагин достаёт сервер по `http://localhost:8787` из iframe и из main-потока;
- IP-адрес в манифесте плагина Figma отклоняет; имя `.local` принимает, но запросы блокирует;
- PNG и JPEG с обоих телефонов вставляются на страницу узлом шириной 400 px, существующие узлы не затрагиваются;
- iOS по умолчанию отдаёт HEIC, в режиме `Compatible` — JPEG;
- iframe плагина не декодирует HEIC;
- изображение 6000×4500 плагин уменьшает до 4096×3072 и вставляет;
- отправка файла через `File.bytes()` и `fetch` из `expo/fetch` работает на обоих телефонах; `fetch(uri).blob()` на Android файл не читает.

### 11.2. Проверено в ходе разработки MVP

**Этап 1, плагин** (2026-10-11, настольное приложение Figma):

- запись в данные документа (`figma.root`), страницы и узла читается сразу; значение документа сохраняется после перезапуска плагина и видно с другой страницы; у каждой страницы свои данные;
- сетка: шаг 440 px, перенос строки на 40 px ниже предыдущей, продолжение сетки после перезапуска плагина;
- изображение 6000×4500 уменьшается до 4096×3072; повреждённый файл даёт `decode_failed` без нового узла;
- повтор задания с тем же идентификатором на другой странице того же файла пропускается;
- существующие узлы не изменяются.

**Этап 2, сервер и плагин вместе** (2026-10-11, отправка через `curl` по адресу Wi-Fi):

- сервер слушает только `127.0.0.1` и адрес интерфейса `en0`; на адресе VPN соединение отклоняется;
- PNG, JPEG 6000×4500 и статичный GIF 500×300 доходят до Figma, статус `inserted` с первой попытки;
- после перезапуска сервера повтор с тем же идентификатором не создаёт второй узел, статус становится `inserted`;
- плагин сам восстанавливает соединение после перезапуска сервера;
- три задания, отправленные при закрытом плагине, ждут в очереди и вставляются после его запуска;
- временная папка пуста после подтверждений.

**Ещё не проверено:**

- чужой объект в следующей ячейке сетки — только автотесты, вручную не проверялось;
- сообщение плагина «Токен не подошёл» — вручную не проверялось;
- анимированный GIF — не поддерживается и не проверялся;
- запрос iOS на доступ к локальной сети и отсутствие запроса доступа к галерее;
- всё, что относится к мобильному приложению (этап 3).

### 11.3. Не проверено, вне MVP

**Development build и сборки для магазинов.** В Expo Go сетевые настройки задаёт сам Expo Go, поэтому проверки из 11.1 на собственную сборку не распространяются.

- iOS: нужны `NSAllowsLocalNetworking` и `NSLocalNetworkUsageDescription`. По документации этого достаточно, на практике не проверено.
- Android: HTTP по умолчанию запрещён. Способ разрешить его для произвольного LAN-IP без глобального флага не найден. Возможные решения: глобальный `usesCleartextTraffic` либо HTTPS.

**Figma в браузере.** Плагин проверялся только в настольном приложении. Импорт локального плагина и доступ к `http://localhost` из браузерной версии не проверялись.

**Публикация плагина в Community.** `devAllowedDomains` действует только при разработке. Для публикации адрес сервера переносится в `allowedDomains` с заполненным `reasoning`.

Это требования платформ. Отдельно от них стоят улучшения для роста числа пользователей: постоянное хранилище очереди, раздельные токены, HTTPS. Публикация сама по себе их не требует.

## 12. Критерии приёмки

### 12.1. Сервер (автоматические тесты)

Авторизация и проверка файлов:

1. Запрос без токена, с неверным токеном и с токеном в URL получает `401`.
2. Файл больше 20 МБ получает `413`; текст под видом PNG — `415`; HEIC — `415`; изображение больше 50 Мп или со стороной больше 16 384 px — `422`.
3. PNG, JPEG и GIF допустимого размера создают задание в `queued` с `attempts = 0`.
4. Preflight `OPTIONS` с `Origin: null` получает нужные заголовки CORS.

Очередь и аренда:

5. `GET /api/jobs/next` выдаёт задания в порядке создания, переводит в `leased`, увеличивает `attempts` и верно считает `pending`.
6. Задание в `leased` повторно не выдаётся, пока аренда не истекла.
7. Через 60 секунд без ответа задание возвращается в `queued` и выдаётся раньше более новых.
8. После третьей выдачи без ответа задание становится `failed` с причиной `plugin_no_ack`, файл удаляется.
9. Задание, не забранное 30 минут, становится `expired`, файл удаляется.
10. Запись о задании удаляется через час после конечного состояния.

Подтверждение и повторы:

11. Подтверждение «вставлено» переводит задание в `inserted` из `leased`, из `queued`, из `failed` и из `expired`. Повторное подтверждение возвращает `200`.
12. Сообщение об ошибке переводит задание в `failed` с переданной причиной. Для задания в `inserted` оно получает `409`.
13. Повторная загрузка с тем же `X-Job-Id` в состояниях `queued`, `leased`, `inserted` не создаёт второе задание и не меняет состояние.
14. Повторная загрузка в состояниях `failed`, `expired` возвращает задание в `queued` с `attempts = 0`.

Состояние подключения:

15. `GET /api/health` без токена отвечает `200` с `service: "mobile-gallery"` и `authorized: false`; с верным токеном — `authorized: true`.
16. `pluginConnected` равен `true` сразу после запроса заданий, `false` через 10 секунд без запросов, и остаётся `true`, пока есть задание с неистёкшей арендой.

Запуск:

17. При старте временная папка очищается.
18. Сервер слушает `127.0.0.1` и адрес указанного интерфейса и не слушает остальные. Без `LAN_INTERFACE` слушает только `127.0.0.1`.

Проверки сроков выполняются с подменой времени, без реального ожидания.

### 12.2. Плагин

**Автоматические тесты** (логика без Figma):

1. Раскладка на пустой странице: первый узел в точке (0, 0).
2. Раскладка на странице с контентом: первый узел у левого края контента, на 100 px ниже его нижней границы.
3. Семь изображений подряд: пять в первой строке с шагом 440 px, два во второй.
4. Вторая строка начинается на 40 px ниже самого высокого узла первой.
5. Повторная отправка продолжает сетку со следующей свободной ячейки и не пересекает ранее вставленные узлы.
6. Если следующая ячейка занята чужим объектом, новый блок начинается ниже всего контента и ни с чем не пересекается.
7. Ни в одном сценарии новый прямоугольник не пересекается с занятыми областями.
8. Размер узла: ширина 400 px, высота по пропорциям; расчёт уменьшения до 4096 px по большей стороне.
9. Список вставленных хранит не больше 500 идентификаторов и находит добавленный.

**Ручная проверка в Figma:**

10. Манифест импортируется без ошибок.
11. Семь изображений ложатся в сетку 5 + 2, пропорции сохранены.
12. Положение и размеры существующих узлов до и после вставки совпадают.
13. Изображение больше 4096 px вставляется после уменьшения.
14. После перезапуска плагина новые изображения продолжают ту же сетку.
15. Объект пользователя, поставленный в следующую ячейку, не перекрывается: новые изображения уходят в новый блок ниже. *(Вручную не проверялось по решению заказчика 2026-10-11; поведение покрыто автотестами 6 и 7.)*
16. Задание с тем же идентификатором, выданное повторно, не создаёт второй узел: на той же странице, на другой странице того же файла, после перезапуска плагина.
17. Плагин закрыт сразу после вставки, до подтверждения: после запуска и повторной выдачи задания второго узла нет.
18. Повреждённый файл даёт запись в списке ошибок, следующие задания обрабатываются.
19. Когда очередь опустела, область просмотра показывает вставленные изображения, выделение не изменилось.

После подключения к серверу (этап 2):

20. При остановленном сервере плагин показывает «Сервер недоступен» и восстанавливается после запуска сервера.
21. При неверном токене плагин показывает «Токен не подошёл».
22. Плагин показывает число ожидающих заданий.

### 12.3. Мобильное приложение (ручная проверка в Expo Go, iOS и Android)

1. Picker открывается без запроса полного доступа к галерее.
2. Можно выбрать несколько изображений, увидеть превью и удалить любое из списка.
3. При отправке у каждого изображения виден свой статус.
4. Адрес и токен сохраняются между запусками приложения.
5. Фото в HEIC с iPhone уходит как JPEG.
6. Приложение показывает разные сообщения в четырёх случаях: сервер выключен; токен неверный; по адресу отвечает другое устройство; сервер работает, а плагин закрыт.
7. При закрытом плагине отправка разрешена, статус «В очереди», видна плашка «Плагин в Figma не запущен».
8. Плашка исчезает не позже чем через 10 секунд после запуска плагина.
9. Для каждого конечного статуса из раздела 5.7 показан свой текст и доступны указанные действия.
10. «Повторить» после ошибки отправки доводит изображение до «Вставлено».

### 12.4. Сквозные сценарии (ручная проверка)

1. Пять изображений с iPhone и пять с Android появляются в Figma, все статусы «Вставлено».
2. Плагин закрыт при отправке: изображения ждут в очереди и вставляются после его запуска.
3. Сервер остановлен во время отправки: после запуска и «Повторить» все изображения вставлены, дубликатов нет.
4. Сервер перезапущен после вставки, на телефоне нажато «Повторить»: дубликатов нет, статус «Вставлено».
5. Плагин закрыт сразу после вставки, до подтверждения: после запуска дубликатов нет, статус «Вставлено».
6. Две отправки подряд с перерывом: изображения второй не перекрывают изображения первой.
7. После смены адреса в настройках телефона отправка работает.

Статусы «Истекло» и «Нет ответа от плагина» вручную не воспроизводятся: они требуют 30 минут ожидания или трёх сбоев подряд. Их переходы покрыты автотестами сервера (12.1, пункты 8 и 9), а тексты на телефоне — пунктом 12.3.9.

## 13. Порядок реализации

Каждый этап заканчивается показом файлов, результатов проверок, инструкции ручной проверки и списка ограничений.

1. **Плагин без сервера.** Вставка, раскладка, уменьшение, защита от дубликатов. Проверяется автотестами логики и на встроенных тестовых изображениях: критерии 12.2, пункты 1–19.
2. **Сервер.** API, очередь, проверка файлов, привязка к интерфейсам, автотесты. После него плагин подключается к серверу: критерии 12.2, пункты 20–22.
3. **Мобильное приложение.** Выбор, отправка, статусы, настройки.
4. **Сквозная проверка** по разделу 12.4 и `docs/connection.md`.
